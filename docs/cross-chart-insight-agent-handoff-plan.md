# 跨盘型解读设计与代理交接规范方案

## 1. 背景

Interstellar 是一个专业占星计算、研究、可视化与解读平台。当前项目已经完成并上线了一版次限盘右侧即时解读设计，它可以作为后续其他盘型的参考样板。

次限盘右侧目前已经形成一套比较清晰的模式：

```text
服务器返回权威计算事实
→ 前端 insight builder 根据事实选择语料
→ 项目内 corpus 提供可复用文案
→ presentation rules 固定模块、视觉和禁忌
→ React 组件渲染固定卡片
→ CSS 独立控制盘型样式
```

这套模式的价值是：

- 不依赖单次聊天上下文；
- 不靠某个模型临场发挥；
- 不把消费者界面写成内部说明；
- 盘面变化后，卡片内容也能按规则变化；
- 其他 agent 或人工工程师接手时，可以快速知道该读什么、该改哪里、不能做什么。

后续设计行运盘、三限盘、日返盘、月返盘、日弧盘等盘型时，都应该按这套方法推进。

## 2. 核心目标

这套规范要解决三个问题。

### 2.1 让不同盘型的解读设计颗粒度一致

以后不是每个盘型随便写几张卡、几段文字，而是每个盘型都必须定义：

- 可靠计算事实；
- 右侧即时解读模块；
- 底部展开解读结构；
- 语料来源；
- 可视化形式；
- 空状态；
- 降级规则；
- 禁忌表达；
- 验证样例。

### 2.2 让不同 agent 可以连续工作

无论是 Codex、DeepSeek、Claude、Cursor，还是人工工程师，接手时都应该知道：

- 当前项目做到哪里；
- 哪些文档是权威入口；
- Obsidian 怎么用；
- 语料如何进入项目；
- 哪些内容不能只停留在聊天记录；
- 做完后如何留下交接记录。

### 2.3 让上下文有限时也能持续遵守规则

模型上下文和记忆都有限，所以必须把重要规则固化到项目文件里，而不是依赖“某一次对话里说过”。

项目需要一个“记忆锚点”：

```text
AGENTS.md
docs/chart-insight-design-standard.md
docs/agent-handoff.md
```

这三个文件共同承担后续接手、设计、审核的入口职责。

## 3. Obsidian 与项目文件的关系

Obsidian 的定位要明确：

```text
Obsidian = 人工维护的调研源 / 知识源 / 语料素材源
项目文件 = 运行时权威源 / 工程实现源 / 验收源
```

后续规则：

1. 缺语料、缺设计、缺解释时，应该先查 Obsidian。
2. Obsidian 中有用的内容，必须迁移或改写进项目内语料/规则文件。
3. 运行时代码不能直接依赖 Obsidian。
4. Obsidian 原文不等于消费者文案，必须过滤内部讨论口吻。
5. 如果 Obsidian 内容不完整，agent 可以补充设计，但补充内容也必须写入项目内文件。
6. 如果 Obsidian 内容和项目规则冲突，以项目内已固化规则为准；必要时更新项目规则，并在交接记录里说明原因。

正确流程不是：

```text
读 Obsidian → 直接写 UI
```

而是：

```text
读 Obsidian
→ 提炼可用语料和设计规则
→ 写入项目内 corpus / presentation rules / docs
→ UI 只消费项目内内容
```

## 4. 服务器、客户端与 AI 的职责边界

后续所有盘型都应该遵守这个边界。

### 4.1 服务器负责权威事实

服务器负责不能由浏览器猜的内容：

- 星历计算；
- 黄道与宫位；
- 点位；
- 相位；
- 跨盘相位；
- ingress / egress / exact 日期；
- 出生地点、时区、经纬度权威解析；
- 账户、保存、权限；
- 可审计 Snapshot；
- 正式报告生成；
- AI 调用代理。

服务器返回的是“可复核事实”。

### 4.2 客户端负责展示层派生

浏览器端可以做：

- 右侧即时解读卡片；
- bar、进度条、标签、圆盘、时间线；
- 根据服务器事实选择语料；
- 空状态；
- 排序和过滤；
- 轻量可视化；
- 不改变事实的文案组织。

比如：

```text
服务器返回：次限月亮 摩羯 4.6°
客户端显示：摩羯阶段进度条 4.6 / 30
```

这是合理的。

### 4.3 客户端不能伪造权威事实

浏览器端不能做：

- 自己重新算星历；
- 自己补服务器没给的相位；
- 自己推断精确日期；
- 自己判断出生时区；
- 自己把弱信号包装成强信号；
- 自己制造不存在的 ingress / egress。

### 4.4 AI 只解释，不计算

AI 或外部模型只能读取已经计算好的事实或技术文档，生成解释文本。

AI 不能：

- 算星盘；
- 改星盘；
- 覆盖服务器事实；
- 生成服务器没有返回的相位、宫位、日期；
- 把推测写成计算结果。

## 5. 盘型解读设计的标准流程

每设计一个新盘型，都按下面流程走。

### 5.1 先读材料

接手者先读：

1. 项目代理入口规范；
2. 跨盘型解读设计标准；
3. 当前项目交接说明；
4. 项目大计划和技术说明；
5. 对应盘型 Obsidian 目录；
6. 已有同类盘型实现，优先参考次限盘。

例如设计日返盘时，应该先读：

```text
obsidian/interstellar/06-日返盘/
app/lib/insight/secondary-presentation-rules.ts
app/lib/insight/secondary-corpus.ts
app/lib/insight/secondary.ts
app/components/workspaces/secondary-instant-insight.tsx
```

不是从空白处自由发挥。

### 5.2 再列可靠事实

先确认这个盘型服务器能返回什么事实。

例如：

- 单盘点位；
- 双盘关系；
- 相位；
- 落宫；
- 精确日期；
- 周期阶段；
- 强度；
- 入相/出相；
- 资料质量；
- 不可用字段。

凡是服务器没有返回、也没有可靠算法支持的，不能进入“计算事实”。

### 5.3 再设计右侧即时解读

右侧即时解读应该回答：

```text
用户一眼看这张盘时，最需要知道什么？
```

每个盘型都要固定右侧模块，而不是每次按样例临时生成。

每个模块必须写清：

- 模块名称；
- 视觉形式；
- 数据来源；
- 语料来源；
- 文案结构；
- 显示条件；
- 空状态；
- 禁忌。

### 5.4 再设计底部展开解读

底部解读不是右侧卡片的重复，而是慢读、复核和展开。

底部每个 tab 要写清：

- tab 名称；
- 解决什么问题；
- 数据来源；
- 内容结构；
- 是否需要表格；
- 是否需要时间线；
- 是否需要解释卡；
- 什么情况下为空或降级。

### 5.5 最后实现分层

实现必须分层：

```text
后端事实
→ insight builder
→ corpus 语料
→ presentation rules 展示规则
→ React 固定模板
→ CSS 独立样式
```

职责：

- 后端：只算事实；
- builder：选择事实、填变量、过滤噪声；
- corpus：提供可复用文案；
- presentation rules：定义模块和禁忌；
- React：只渲染固定结构；
- CSS：只控制视觉。

## 6. 每个盘型必须具备的设计规格

每个新盘型开始实现前，至少要写清下面这些内容。

```text
盘型目标：
用户打开这个盘最想知道什么？

可靠事实：
服务器能返回哪些事实？哪些不能返回？

右侧模块：
固定几张卡？每张卡说什么？用什么可视化？

底部解读：
有哪些 tab？每个 tab 用什么阅读结构？

语料：
哪些来自 Obsidian？哪些已迁移进项目？哪些还缺？

可视化：
哪些事实用进度条、堆叠条、时间线、标签、卡片、表格？

降级：
缺出生时间、缺地点、缺相位、无强信号时怎么显示？

禁忌：
哪些表达不能出现？

验证：
用哪些样例证明不是只适配当前盘？
```

如果这些没有写清，就不应该直接进入 UI 实现。

## 7. 事实类型与可视化映射规则

后续盘型都应优先使用这套映射。

| 事实类型 | 推荐可视化 | 适用条件 | 文案结构 | 禁忌 |
|---|---|---|---|---|
| 当前阶段 | 阶段卡 / 进度条 | 有连续区间、度数、日期范围 | 当前处于什么阶段 + 走到哪里 | 不写成好坏分 |
| 周期位置 | 圆盘 / 环形进度 / 月相图 | 有 0-360° 或周期比例 | 周期名称 + 阶段含义 | 不写成事件预测 |
| 支持/挑战/中性数量 | 堆叠条 | 分类互斥且总量有意义 | 结构比例 + 一句解释 | 不写成好运坏运 |
| 强触发 | 信号卡 / Top 3 | 强度高、容许度小、exact/applying | 哪个移动点触发哪个本命点 | 不只显示术语 |
| 换座/换宫/交界 | 时间线 / 节点 | 有 ingress/egress/exact 日期 | 旧阶段 → 新阶段 | 没日期不假造 |
| 多领域热点 | 标签组 / 小卡片 | 多个落宫/主题聚合 | 本命第 X 宫 + 现实领域语言 | 不额外造设计外模块 |
| 无强信号 | 空状态卡 | 信号不足或条件不满足 | 当前较平稳 + 看什么 | 不硬凑解释 |
| 资料不足 | 降级提示 | 缺出生时间/地点/目标日期 | 哪些内容不可判定 | 不偷偷补默认值 |
| AI 深度解释 | 独立入口 | 用户同意且服务端配置 | AI 只解释已算事实 | AI 不计算、不改事实 |

## 8. 右侧即时解读模块的设计规则

右侧不是报告，它是“快速看懂这张盘”。

右侧模块应该：

- 固定数量；
- 固定职责；
- 固定视觉；
- 能随盘面事实变化；
- 有空状态；
- 不暴露内部模板；
- 不把术语堆给用户；
- 不输出确定事件预测。

次限盘右侧样板是：

1. 当前人生阶段；
2. 长期变化主题；
3. 核心转折点；
4. 阶段建议；
5. 与本命盘的关系。

其他盘型可以不照抄名字，但要达到同等颗粒度。

例如行运盘可能是：

1. 当前外部触发；
2. 近期压力与支持；
3. 最强本命触点；
4. 时间窗口；
5. 应对建议。

例如日返盘可能是：

1. 年度主题；
2. 年度重点领域；
3. 年度关系/事业/自我焦点；
4. 关键转折月份；
5. 与本命盘的年度叠加。

这些只是示例，真正设计时必须根据 Obsidian 和计算事实定稿。

## 9. 底部展开解读的设计规则

底部不是右侧的重复。

右侧回答：

```text
我现在一眼应该看什么？
```

底部回答：

```text
为什么这样看？具体事实是什么？有哪些层次？
```

底部适合：

- 读法说明；
- 月亮/太阳/主星等核心点展开；
- 本命触发；
- 落宫；
- 相位；
- 时间线；
- 证据与来源；
- 技术表格；
- AI 深度分析入口。

每个 tab 必须有固定结构，不要随当前样例临时拼。

## 10. 语料设计规则

语料必须项目化。

每个盘型应该有类似：

```text
app/lib/insight/{chart}-corpus.ts
app/lib/insight/{chart}-presentation-rules.ts
```

语料要按事实类型组织，而不是按当前样例写死。

语料应该支持变量：

```text
{moving_point}
{reference_point}
{sign}
{house}
{aspect}
{state}
{date_range}
{phase}
```

语料缺失时：

1. 先查 Obsidian；
2. 提取有用内容；
3. 改写成消费者可读文案；
4. 写入项目 corpus；
5. 如果仍缺，补充合理 fallback；
6. 在交接文档里记录缺口。

语料禁忌：

- 不要吓人；
- 不要下确定命运判断；
- 不要把挑战写成坏事；
- 不要把支持写成必然好运；
- 不要把内部说明给用户看；
- 不要为了凑字数写空泛段落。

## 11. 项目需要新增的三个规范入口

### 11.1 `AGENTS.md`

用途：所有 agent / 接手者的第一入口。

内容应该包括：

- 接手前必读顺序；
- Obsidian 使用规则；
- 服务器/客户端/AI 边界；
- 盘型解读分层；
- 禁止事项；
- 验证要求；
- 做完后必须更新交接文档。

### 11.2 `docs/chart-insight-design-standard.md`

用途：跨盘型解读设计标准。

内容应该包括：

- 总原则；
- 事实 → 可视化映射；
- 右侧模块规则；
- 底部 tab 规则；
- 语料规则；
- 降级规则；
- 禁忌；
- 次限盘样板；
- 新盘型设计模板。

### 11.3 `docs/agent-handoff.md`

用途：上下文交接。

内容应该包括：

- 当前主分支；
- 最新生产部署；
- 最近重要提交；
- 已完成能力；
- 未完成能力；
- 接手前必读；
- 最近完成；
- 当前设计样板；
- 下一步注意事项；
- 未解决问题。

这份文件以后每次重要任务后都要更新。

## 12. 架构守门建议

为了让规范不是“写了没人遵守”，需要把一部分规则加进架构检查。

建议更新 `scripts/check-architecture.mjs`。

### 12.1 检查规范文件存在

必须存在：

```text
AGENTS.md
docs/chart-insight-design-standard.md
docs/agent-handoff.md
```

### 12.2 检查运行时代码不依赖 Obsidian

`app/` 下不能 import 或读取：

```text
obsidian/
```

文档可以提 Obsidian，运行时代码不能依赖。

### 12.3 检查消费者代码禁忌词

在 `app/components` 和 `app/lib/insight` 中禁止出现：

```text
人话
怎么用
别误读
模板回答
这张卡回答
```

如果这些词出现在文档的“禁忌”说明里可以允许，但不能出现在消费者展示逻辑里。

### 12.4 检查次限盘样板不退化

确认这些文件存在：

```text
app/lib/insight/secondary-corpus.ts
app/lib/insight/secondary-presentation-rules.ts
app/lib/insight/secondary.ts
app/components/workspaces/secondary-instant-insight.tsx
```

确认次限盘五个模块 id 仍存在：

```text
current-stage
change-themes
turning-points
stage-advice
natal-link
```

### 12.5 检查 page.tsx 保持薄入口

继续保持：

- 不写 `"use client"`；
- 不持有 React state；
- 不直接 fetch；
- 不超过合理行数。

## 13. 后续 agent 执行任务时的标准提示

以后给任何 agent 工具任务时，可以这样说：

```text
你现在接手 Interstellar 项目。先阅读 AGENTS.md、docs/agent-handoff.md、docs/chart-insight-design-standard.md，再阅读当前任务对应的 Obsidian 盘型目录和已有同类盘型代码。

任务：按跨盘型解读设计规范推进当前盘型。Obsidian 是人工维护的调研/语料源；缺语料时先查 Obsidian，有用内容迁移或改写进项目内 corpus/rules；运行时代码不得依赖 Obsidian。

服务器只负责权威计算事实；浏览器负责展示层派生；AI 只能解释已算事实，不能计算或覆盖事实。

不要把内部说明写进消费者 UI。不要改无关业务。完成后运行 npm run architecture:check 和 npm run lint -- --quiet，并更新 docs/agent-handoff.md。
```

## 14. 审核清单

后续任何 agent 做完后，审核者应该检查：

- 是否读过并遵守 `AGENTS.md`；
- 是否把 Obsidian 的有用内容迁移进项目，而不是运行时依赖；
- 是否明确服务器/客户端/AI 边界；
- 是否有项目内 corpus 和 presentation rules；
- 是否达到次限盘同等颗粒度；
- 是否有固定右侧模块和底部结构；
- 是否有空状态和降级规则；
- 是否避免内部话术进入消费者 UI；
- 是否避免硬编码当前样例；
- 是否更新交接文档；
- 是否通过架构检查和 lint；
- 是否没有误改部署、分支、密钥或无关业务。

## 15. 当前次限盘状态记录

当前次限盘右侧可以作为参考样板。

已固化内容：

- 右侧五张卡 A-E；
- 卡片模块规则；
- 项目内语料；
- 事实选择逻辑；
- 噪声过滤；
- 月亮/太阳阶段进度；
- 月相圆盘；
- 支持/挑战/中性 bar；
- 核心转折点固定三行；
- 阶段建议固定三条；
- 与本命关系固定结构；
- 独立 CSS；
- 架构检查。

尚未完全固化内容：

- 底部展开解读仍需后续专项设计；

- 交接文件尚需建立；
- 架构检查还可以继续强化。
