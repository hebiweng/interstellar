## 1. 项目摘要

Interstellar V1是面向职业占星师、占星学习者和重度爱好者的西方占星专业计算平台。项目第一阶段不以AI解读、消费者内容或交易服务作为竞争点，而是先建立完整、可验证、可追溯的专业计算、图形和研究工作流。

项目采用“完整能力边界 + 分阶段成熟度”的策略：V1覆盖现代、古典与希腊化西方占星的主要计算体系，但每项能力根据验证程度标记为`Stable`、`Beta`或`Experimental`。未通过验证的能力可以存在，但不得包装为稳定能力。

V1同时交付：

- 专业Web工作台；
- 版本化REST API与TypeScript/Python SDK；
- 本地Docker Compose部署；
- 官方数据本地版本化；
- Canonical Astrology Schema；
- 算法卡、金标准、差异测试和专业复核制度；
- 全量计算、图形、数据导出和可重导入项目归档。

详细技术实现以[V1技术开发说明书](./v1-development-spec.md)为准，能力状态以[能力矩阵](./capabilities.yaml)为准。

## 2. 项目目标与成功标准

### 2.1 业务目标

1. 建立一个可以被专业用户长期使用和校验的西方占星计算底座。
2. 用统一Schema、版本和证据链降低不同技法、不同图表之间的数据割裂。
3. 通过开源和公共API获取早期专业用户反馈，沉淀验证案例和规则资产。
4. 为后续消费者产品、AI解释、新占术插件和商业服务提供稳定平台层。

### 2.2 V1成功标准

- 能力矩阵中所有`v1_required: true`项目已实现，并达到目标成熟度或公开降级原因；
- 关键天文位置、宫位、轴点和时间命中通过金标准与独立差异测试；
- 职业用户能完成建档、计算、比较、分屏、证据检查、保存和导出；
- 同一输入在固定引擎、规则和数据版本下可以完全复现；
- Web、API、SDK、导出和项目归档使用同一Canonical Schema；
- 完成中英文界面与核心文档；
- Docker Compose在全新环境中可按文档部署、备份、升级和恢复；
- 完成数据许可、开源许可、隐私、安全和专业评审；
- 未引入核心数据爬虫、付费数据库和商业内容逆向。

### 2.3 不作为V1成败指标

- 大规模消费者注册数；
- 会员收入或咨询交易额；
- AI对话质量；
- 每日运势打开率；
- 企业级可用性和多区域容灾；
- 对现实事件的确定性预测准确率。

## 4. 执行策略

### 4.1 研发原则

- **纵向切片优先**：先打通输入—时间—计算—快照—图形—导出的全链路，再扩展技法数量。
- **Schema先行**：公共结构先写Schema和契约测试，前后端从同一Schema生成类型。
- **算法卡先行**：复杂技法先确定流派、公式、参数和测试样本，禁止边写边猜。
- **验证早于Stable**：实现完成不等于Stable；Stable必须通过金标准、差异测试和专业复核。
- **按成熟度交付**：范围大不等于一次全部稳定，Beta/Experimental公开展示限制。
- **数据本地化**：运行时使用本地版本化数据，不让核心计算依赖公共在线API。
- **单人可维护**：V1采用模块化单体、单区域和Docker Compose，控制运维复杂度。

### 4.2 阶段门禁

每个阶段按以下顺序推进：

```text
范围和算法卡
→ Schema/API
→ 计算实现
→ 单元/属性测试
→ 金标准/差异测试
→ UI和导出
→ 文档和数据来源
→ 阶段评审
```

未通过阶段门禁的能力可以延后或降低成熟度，不得通过删除警告或放宽测试伪装完成。

## 5. 24个月路线图

### 5.1 M0—M1：规范与基础设施

**目标**：形成可以持续扩展的技术骨架和第一条空结果链路。

交付：

- Monorepo、CI、代码质量和Docker Compose；
- Next.js、FastAPI、Worker、PostgreSQL/PostGIS、Redis、MinIO；
- Canonical Schema和TS/Python类型生成；
- Workspace、Subject、SubjectVersion、TimeSpec、Location；
- RLS、字段加密接口、审计框架；
- DatasetVersion、数据Manifest和许可证台账；
- Swiss Ephemeris Adapter与JPL校验框架；
- 三栏工作台壳层、API错误协议、任务状态机。

验收：输入出生资料后，系统能完成时间标准化、对象版本创建，并生成带完整版本元数据的空计算快照。

退出条件：

- 正常时间、DST重复、DST空洞和未知时间测试通过；
- SubjectVersion不可变且RLS越权测试通过；
- 全新环境能用Compose启动；
- 第一个数据Manifest具备来源、版本、校验和与许可。

### 5.2 M2—M6：Professional Alpha

**目标**：专业用户可完成基础排盘、关系比较、行运查看和导出。

交付：

- 本命、行运、比较盘、组合盘、太阳返照和月亮返照；
- 主要天体、节点、四轴、宫位、相位、逆行、元素和模式；
- 单轮、双轮、相位网格、位置表和基础时间线；
- 匿名计算、云端保存、不可变版本和计算历史；
- SVG、PNG、JSON、CSV导出；
- REST API、异步Job、SSE、取消、超时和限流；
- 首批金标准、JPL差异测试和视觉回归；
- 中英文核心术语与错误。

Alpha验收场景：

1. 用户匿名输入一份精确出生资料并生成本命盘；
2. 用户注册后保存资料、修改时间并形成第二版本；
3. 旧盘仍引用第一版本，结果不变化；
4. 用户创建第二人并生成比较盘、组合盘；
5. 用户选择日期生成行运和太阳返照；
6. 用户查看结构化位置、相位、警告和数据版本；
7. 用户导出SVG、PNG、JSON和CSV；
8. API客户端完成相同流程并获得一致结果。

阶段决策：Alpha后进行一次职业用户测试。如果核心时间和图形工作流仍不稳定，优先修复，不提前扩展消费者功能。

### 5.3 M7—M12：预测、关系与图形Beta

**目标**：覆盖专业预测和研究所需的主流中高级能力。

交付：

- 次限、三限、太阳弧、戴维森盘；
- 中点、谐波、尊贵、接纳、格局、阿拉伯点；
- 固定星和常用小行星；
- 统一事件搜索器、精确时间和逆行多次触发；
- 图形星历、行运甘特、返照日历；
- 三轮、四轮、中点树、专业数据表；
- PDF、ICS和可重导入项目归档；
- Natural Earth底图和可替换OSM服务；
- 精选公开案例回归库；
- Rule Pack Runtime第一版。

验收：专业用户可完成年度预测研究、复杂关系研究、多图对照和完整项目交付；归档导入后结构化结果保持一致。

### 5.4 M13—M18：古典与专项Pro

**目标**：补齐古典、时间主星、问事、择时和地理能力。

交付：

- 年度/月度/日度小限、法达、黄道释放和行星周期；
- 主限、其他弧向、赤纬技法和高级返照；
- 卜卦盘有效性、象征星、接纳、入相、完成和时间规则；
- 择时硬约束、加分规则、候选扫描和排序；
- 迁移盘、Astrocartography、Local Space、Paran和城市比较；
- Rule Pack编辑、验证、版本和Preset；
- 事业、关系、财务、项目的结构化证据链；
- 活跃度、支持度、压力度和确定度独立输出。

验收：每个专项能力至少具备已批准算法卡、金标准样本和公开限制；无算法卡项目不得进入Stable候选。

### 5.5 M19—M24：完整西方占星V1

**目标**：完成能力矩阵、稳定公共接口并形成可公开交付的专业平台。

交付：

- 世运、国家盘、公司盘、项目盘和食相分析；
- 动态关系预测和多技法联合时间线；
- 历史相似周期检索；
- V1图形家族补齐；
- 中英文、键盘、打印和色盲可用性；
- TypeScript/Python SDK；
- Docker Compose自托管、备份、恢复和升级手册；
- 性能、安全、隐私和许可证审计；
- 职业占星师评审和最终能力矩阵；
- V1已知限制与后续路线发布。

验收：达到技术说明书中的V1门禁。未达到目标成熟度的能力必须明确降级，并在能力矩阵记录原因、缺失测试和后续计划。

## 6. 资源计划

### 6.1 人员

| 角色 | 配置 | 职责 |
|---|---:|---|
| 产品/技术负责人 | 1人，持续 | 范围、架构、实现、测试、发布和运维 |
| AI辅助 | 持续 | 代码草案、测试生成、文档整理、差异分析；不得作为算法权威 |
| 西方占星专业评审 | 里程碑按需 | 算法卡、流派差异、样本和Stable评审 |
| 安全/许可审查 | M6、M12、M24按需 | RLS、加密、归档、开源和数据许可 |
| 双语校对 | M6、M18、M24按需 | 中英文术语和用户文案一致性 |

单人开发的直接后果：

- 不并行维护微服务、多云、多原生客户端；
- 每阶段最多一个核心计算工作包和一个平台工作包处于开发中；
- 范围不通过砍掉验证保证进度，而通过成熟度分级和阶段顺序控制；
- 专业评审是Stable门禁，AI输出不能代替人工评审。

### 6.2 成本策略

V1默认不采购数据许可，主要成本为：

- 单区域服务器、数据库、对象存储和流量；
- 域名、邮件、备份和监控；
- 专业占星算法评审；
- 安全和许可证专项审查；
- 必要的地图瓦片或地理编码服务；
- 开发与AI工具。

成本控制措施：

- AGPL使用Swiss Ephemeris；
- 官方数据本地化，不按请求调用收费天文API；
- 常用恒星和小行星内置，长尾对象按需缓存；
- Natural Earth承担全球底图；详细地图采用可替换供应商；
- 公共服务限流、排队和按优先级降级；
- V1不承诺SLA，不为高峰提前建设分布式架构。

### 6.3 什么时候必须付费

以下情况发生时启动采购评估：

| 触发条件 | 可能采购 |
|---|---|
| 产品闭源或提供不兼容AGPL的商业服务 | Swiss Ephemeris Professional License |
| 公共地图流量超过自建能力或免费政策 | 商业瓦片/地理编码服务 |
| 需要企业级监控、备份或多区域 | 云基础设施和可观测性服务 |
| 需要商业使用的高质量名人出生时间库 | 书面数据授权；若无授权则不做 |
| 需要商业报告文本和专业规则 | 原作者授权、顾问或自建内容团队 |
| 专业Stable评审无法由社区完成 | 付费占星师评审 |

## 7. 数据策略与覆盖判断

### 7.1 免费来源能否覆盖V1

结论：在项目整体采用AGPL、算法自行实现、核心数据本地化的前提下，免费官方数据能够覆盖V1的确定性计算和制图需求。

免费数据能够覆盖：

- 太阳、月亮、行星、节点、宫位、轴点、速度、逆行；
- 地心、日心和拓扑中心坐标；
- 小行星轨道、固定星天文位置；
- 现代时区、DST、全球地点和时区边界；
- 地球定向、闰秒、日月食校验；
- 世界底图和可授权的详细地图数据；
- 由上述事实派生的相位、格局、中点、谐波、返照、推运、合盘、地理线和绝大多数图形。

免费数据不能自动提供：

- 完整且可靠的1970年前地方时间事实；
- 大量人物经验证的精确出生时间；
- 商业可用的中文解释文本；
- 公认的主题评分权重和事件概率；
- 出生时间校正的标准答案；
- 企业级托管、地图瓦片和查询SLA；
- 商业软件专有算法和内容。

### 7.2 数据获取边界

| 分类 | 做法 |
|---|---|
| 官方发布包/Dump | 允许，保存版本、校验和、许可和署名 |
| 官方API/TAP | 允许，遵守限流，按需缓存并记录查询来源 |
| 手工授权导入 | 允许，保存授权范围和来源 |
| 公共网页抓取 | 不作为核心数据来源 |
| Astro-Databank爬虫 | 禁止 |
| 公共Nominatim批量/自动完成 | 禁止 |
| 商业App报告和规则抓取 | 禁止 |
| Google地图数据提取 | 禁止 |

具体来源、URL和同步频率见技术说明书第10节。

## 8. 质量、发布与变更管理

### 8.1 发布通道

| 通道 | 对象 | 承诺 |
|---|---|---|
| `nightly` | 开发和自动测试 | 不保证数据迁移和API稳定 |
| `alpha` | 早期专业测试者 | 核心工作流可用，允许破坏性变更 |
| `beta` | 更广专业用户 | 迁移可控，变更有公告，能力限制公开 |
| `v1` | 正式开源和自托管 | `/api/v1`兼容、迁移文档、已知限制和安全修复 |

### 8.2 变更规则

- 需求变更先更新本计划和能力矩阵，再进入研发任务；
- 新增技法必须有算法卡、负责人、阶段和成熟度目标；
- 删除或延后`v1_required`能力必须记录理由和影响；
- 数据版本升级必须跑完整金标准和差异测试；
- 公共字段重命名或语义变化必须发布新Schema版本；
- V1发布后，`/api/v1`只允许向后兼容新增和错误修复。

### 8.3 阶段评审材料

每次阶段评审提供：

- 能力矩阵变化；
- 已通过和失败的金标准；
- 差异测试报告；
- 性能、错误和队列指标；
- 数据和许可证变化；
- 已知问题、技术债和安全问题；
- 用户反馈与下一阶段调整；
- Stable/Beta/Experimental变更建议。

## 9. 风险登记

| 风险 | 概率 | 影响 | 预警信号 | 缓解与应对 |
|---|---|---|---|---|
| 单人团队范围过大 | 高 | 高 | 连续两个里程碑延期 | 纵向切片、限制并行、成熟度降级，不提前做消费者功能 |
| 高级技法流派冲突 | 高 | 高 | 同名能力结果不一致 | 算法卡明确流派和参数，允许并列变体，不静默合并 |
| 历史时区错误 | 高 | 高 | 同地点同时间存在权威冲突 | 候选结果、可信度、人工修正、数据版本和警告 |
| Swiss许可误用 | 中 | 高 | 出现闭源或非AGPL发行需求 | V1保持AGPL；商业化前采购专业许可和法律审查 |
| 专业评审不足 | 中 | 高 | 大量能力停留Beta | 早期建立评审关系，Stable数量服从评审容量 |
| 数据源政策变化 | 中 | 中 | API限流或许可调整 | 本地版本化、可替换Adapter、许可证台账和同步告警 |
| 图形性能不足 | 中 | 中 | 大型盘SVG过大、交互卡顿 | SVG/Canvas/WebGL分层、符号聚合、异步导出 |
| 任务队列拖垮公共服务 | 中 | 高 | 排队时间和超时持续上升 | 限流、配额、优先级、取消、任务预算和降级 |
| 用户敏感资料泄露 | 低到中 | 极高 | 日志含出生资料或越权测试失败 | RLS、应用层加密、日志脱敏、安全门禁、短期分享 |
| API与Schema漂移 | 中 | 高 | TS/Python结果不一致 | 单一Schema源、代码生成、契约测试和版本策略 |
| 主题评分被误解为预测 | 高 | 中 | 用户传播“成功概率” | 分拆活跃/支持/压力/确定度，展示证据和非确定性说明 |
| 免费地图服务不可用 | 高 | 中 | 限流或瓦片失败 | Natural Earth本地底图、供应商Adapter、自建或采购 |

## 10. V1后拓展路线

### 10.1 消费端产品

前置条件：V1核心计算稳定、主题证据链可解释、具备至少一个完整用户研究周期。

后续能力：

- 简化出生资料输入和引导；
- 个人、关系、职业、年度专题报告；
- 每日、每月、每年主题时间线；
- 事件、情绪、关系和项目记录；
- 每周/每月复盘和历史周期对照；
- 关系邀请、双方权限和共同档案；
- 订阅和单次报告。

### 10.2 AI能力

前置条件：Canonical Snapshot、Evidence和Rule Pack稳定。

后续能力：

- 根据结构化证据链解释计算结果；
- 自然语言筛选和控制图表；
- 结合用户授权记录进行长期复盘；
- 报告生成、问题澄清和多语言表达；
- 对相互矛盾的证据进行显式综合。

约束：AI不得直接计算行星位置、宫位和精确相位；不得把推断写回计算事实；不得输出确定性灾难、医疗、法律或投资结论。

### 10.3 新占术插件

平台层预留统一Envelope：插件ID、版本、输入、TimeSpec、Location、来源、成熟度、Evidence、Job和Export。每个系统使用独立领域Schema。

候选顺序由后续市场和专业资源决定：

- 印度占星；
- 八字；
- 紫微斗数；
- 奇门遁甲；
- 其他历法和占术系统。

V1不为这些系统伪造通用“星盘字段”，只提供公共平台协议。

### 10.4 专业商业能力

- 占星师客户管理、咨询前问卷和报告交付；
- 预约、支付、退款和争议处理；
- 团队Workspace、角色、审计和机构模板；
- 商业API、计量、API Key管理和SLA；
- 课程、案例库和专业认证工具。

### 10.5 基础设施升级

- Kubernetes或托管容器；
- 多区域读取、备份和灾难恢复；
- 分布式任务和分析型数据库；
- 全量或分层星表、小行星和地图镜像；
- 企业级密钥管理、审计和合规；
- 商业地图、地理编码和数据授权。

## 11. 暂时无法可靠实现的能力

以下项目写入路线但不承诺在V1解决：

| 能力 | 当前障碍 | V1处理 | 后续条件 |
|---|---|---|---|
| 1970年前全部历史时区唯一答案 | 原始记录不完整且数据源冲突 | 返回候选、可信度、来源和人工修正 | 专项历史资料与地区数据库 |
| 唯一出生时间校正结果 | 无标准答案、不同流派可冲突 | Experimental，多候选，不承诺唯一值 | 专业案例库和可审计方法研究 |
| 全量公众人物精确出生时间 | 数据稀缺、许可和来源质量不一 | 只做Wikidata+授权精选案例 | 获得书面授权和持续校验能力 |
| 事业/感情/项目客观概率 | 无行业统一权重和科学验证 | 只输出活跃/支持/压力/确定度 | 用户反馈研究和明确产品边界 |
| 完整中文解释文本库 | 版权和专业写作成本 | V1只输出结构化证据 | 自建内容团队或合法授权 |
| 校时算法标准验证集 | 缺少真实出生时刻标准答案 | 仅研究功能 | 授权记录、盲测和长期事件数据 |
| 全量Gaia/OSM/小行星镜像 | 存储、更新和计算成本过高 | 常用内置、长尾按需缓存 | 规模化基础设施和预算 |
| 商业软件专有能力复刻 | 版权、合同和不可验证实现 | 明确禁止 | 取得授权或独立公开方法实现 |
| 企业级SLA | 单人团队、单区域架构 | 无SLA，限流和降级 | 专职运维、多区域和预算 |
| 闭源商业发行 | Swiss Ephemeris AGPL约束 | V1整体AGPL | 购买专业许可并完成法律审查 |

## 12. 项目治理与最终交付

### 12.1 每周

- 更新工作包、阻塞和能力矩阵；
- 检查失败测试、性能回退和数据同步；
- 只保留一个核心算法工作包处于主开发状态；
- 将新增流派差异写入算法卡，不留在聊天或代码注释中。

### 12.2 每月

- 对照本计划检查里程碑偏差；
- 发布内部演示和变更日志；
- 审查数据、依赖和许可证更新；
- 检查备份恢复和安全告警；
- 确定下一月的Stable候选，而不是仅按功能数量排期。

### 12.3 每阶段

- 完成阶段验收场景；
- 邀请专业评审审核算法卡和结果；
- 发布已知限制和成熟度变化；
- 决定继续、修复、降级或延后的能力；
- 不因路线压力跳过时间、许可、隐私和结果可复现性门禁。

### 12.4 V1最终交付清单

- Web专业工作台；
- FastAPI服务和异步Worker；
- PostgreSQL/PostGIS、Redis和MinIO部署；
- `/api/v1` OpenAPI与TS/Python SDK；
- Canonical Schema和RenderSpec；
- V1计算和图形能力；
- Rule Pack Runtime和官方规则包；
- 金标准、差异测试、视觉回归和E2E测试；
- 数据Manifest、许可台账和署名；
- Docker Compose、备份、恢复、迁移和升级文档；
- 中英文用户和开发文档；
- 最终能力矩阵、算法卡、专业评审和已知限制；
- V1后消费者、AI、新占术、商业与基础设施路线。
