# 跨盘型解读设计标准

> 所有盘型的解读设计都应遵守本文件。次限盘是当前参考样板。

---

## 1. 总原则

1.1 每个盘型的解读必须基于服务器返回的可靠计算事实，不能凭空生成。

1.2 每个盘型都必须定义完整的设计规格，不能只写几张卡片就进入实现。

1.3 右侧即时解读回答"用户一眼应该看什么"，底部展开解读回答"为什么这样看、具体事实是什么"。

1.4 语料必须项目化，运行时不能依赖 Obsidian。

1.5 所有消费者可见文案必须从项目内语料库引用，不能从 Obsidian 或聊天记录直接输出。

1.6 同一事实在不同卡片中只解释一次，其余位置引用不重复。

1.7 视觉设计不是装饰。仪表、波形、雷达、环形图、时间线、矩阵等必须表达真实事实关系，不能用随机数或示例分数填充正式界面。

1.8 有 Obsidian 视觉示意的卡片，必须还原其信息结构和核心视觉。通用进度条或普通列表不能替代已指定的专属视觉。

1.9 消费者界面先给可理解的结论，再提供事实与术语；不能把计算参数、边界声明或使用说明当成摘要。

1.10 中文界面只出现中文，英文界面只出现英文；默认英文。两种语言分别验收长文本、截断和语气。

## 2. 事实类型与可视化映射

后续盘型都应优先使用这套映射。

| 事实类型 | 推荐可视化 | 适用条件 | 文案结构 | 禁忌 |
|---|---|---|---|---|
| 当前阶段 | 阶段卡 / 进度条 | 有连续区间、度数、日期范围 | 当前处于什么阶段 + 走到哪里 | 不写成好坏分 |
| 周期位置 | 圆盘 / 环形进度 / 月相图 | 有 0-360° 或周期比例 | 周期名称 + 阶段含义 | 不写成事件预测 |
| 支持/挑战/中性数量 | 堆叠条 | 分类互斥且总量有意义 | 结构比例 + 一句解释 | 不写成好运坏运 |
| 强触发 | 信号卡 / Top 3 | 强度高、容许度小、exact/applying | 哪个移动点触发哪个本命点 | 不只显示术语 |
| 换座/换宫/交界 | 时间线 / 节点 | 有 ingress/egress/exact 日期 | 旧阶段 → 新阶段 | 没日期不假造 |
| 多领域热点 | 标签组 / 小卡片 | 多个落宫/主题聚合 | 本命第 X 宫 + 现实领域语言 | 不额外造设计外模块 |
| 无强信号 | 空状态卡 | 信号不足或条件不满足 | 当前较平稳 + 看什么 | 不硬凑解释 |
| 资料不足 | 降级提示 | 缺出生时间/地点/目标日期 | 哪些内容不可判定 | 不偷偷补默认值 |
| AI 深度解释 | 独立入口 | 用户同意且服务端配置 | AI 只解释已算事实 | AI 不计算、不改事实 |

## 3. 右侧即时解读模块规则

### 3.1 设计要求

右侧不是报告，它是"快速看懂这张盘"。

右侧模块应该：
- 固定数量
- 固定职责
- 固定视觉
- 能随盘面事实变化
- 有空状态
- 不暴露内部模板
- 不把术语堆给用户
- 不输出确定事件预测

### 3.2 每个模块必须写清

- 模块名称（含 id）
- 视觉形式
- 数据来源（服务器字段名）
- 语料来源（corpus_id 范围）
- 文案结构
- 显示条件
- 空状态
- 禁忌

### 3.3 右侧模块定义文件

每个盘型必须有一个 `presentation-rules.ts` 文件，导出模块配置数组。模块 id 在文件中固定，不能运行时动态生成。

### 3.4 次限盘样板（5 张卡片）

| 模块 id | 标题 | 核心内容 |
|---|---|---|
| `current-stage` | 当前人生阶段 | 月相圆盘 + 次限月亮/太阳星座进度条 |
| `change-themes` | 长期变化主题 | 支持/挑战/中性色条 + 三张主题小卡 |
| `turning-points` | 核心转折点 | 固定三行：核心相位/月亮阶段/月相 |
| `stage-advice` | 当前阶段建议 | 行动方向标签 + 固定三条建议 |
| `natal-link` | 与本命盘的关系 | 被强化/被挑战两列 + 新可能 |

### 3.5 其他盘型示例颗粒度

其他盘型可以不照抄名字和数量，但要达到同等颗粒度。例如：

**行运盘**（5 张）：
1. 当前外部触发
2. 近期压力与支持
3. 最强本命触点
4. 时间窗口
5. 应对建议

**日返盘**（5 张）：
1. 年度主题
2. 年度重点领域
3. 年度关系/事业/自我焦点
4. 关键转折月份
5. 与本命盘的年度叠加

**天象盘**（8 张）：
1. 当前天空总览
2. 核心天象主题
3. 关键天象事件
4. 天空结构与张力
5. 集体领域影响
6. 观察重点与个人联动
7. 天象演进
8. 行星速览

## 4. 底部展开解读规则

### 4.1 底部与右侧的关系

底部不是右侧的重复。

- 右侧回答：我现在一眼应该看什么？
- 底部回答：为什么这样看？具体事实是什么？有哪些层次？

### 4.2 每个 Tab 必须写清

- Tab 名称
- 解决什么问题
- 数据来源
- 内容结构
- 是否需要表格
- 是否需要时间线
- 是否需要解释卡
- 什么情况下为空或降级

### 4.3 底部适合的内容

- 读法说明
- 核心天体展开（月亮/太阳/主星等）
- 本命触发
- 落宫
- 相位
- 时间线
- 证据与来源
- 技术表格
- AI 深度分析入口

### 4.4 Tab 结构必须固定

每个 Tab 有固定结构，不要随当前样例临时拼。具体事实可以变，但阅读框架不变。

## 5. 语料规则

### 5.1 语料必须项目化

每个盘型应该有：

```text
app/lib/insight/{chart}-corpus.ts
app/lib/insight/{chart}-corpus-combinations.ts
app/lib/insight/{chart}-presentation-rules.ts
```

### 5.2 语料按事实类型组织

语料要按事实类型组织，而不是按当前样例写死。

### 5.3 语料应支持变量

```text
{moving_point}    — 移动点名称
{reference_point} — 参考点名称
{sign}            — 星座
{house}           — 宫位
{aspect}          — 相位类型
{state}           — 运行状态
{date_range}      — 日期范围
{phase}           — 阶段
{planet_a}        — 行星A
{planet_b}        — 行星B
{theme}           — 主题
{direction}       — 方向（支持/压力/转换）
{duration}        — 持续时间
{intensity}       — 强度等级
```

### 5.4 语料缺失时处理流程

1. 先查 Obsidian
2. 提取有用内容
3. 改写成消费者可读文案
4. 写入项目 corpus
5. 如果仍缺，补充合理 fallback
6. 在交接文档里记录缺口

### 5.5 语料禁忌

- 不要吓人
- 不要下确定命运判断
- 不要把挑战写成坏事
- 不要把支持写成必然好运
- 不要把内部说明给用户看
- 不要为了凑字数写空泛段落

---

## 6. 降级规则

每种缺条件场景都必须定义降级显示，不能跳过或假设默认值。

| 缺失条件 | 降级策略 |
|---|---|
| 缺出生时间 | 不显示宫位、上升、天顶相关内容；显示提示"需要出生时间" |
| 缺出生地点 | 不显示当地宫位和角度；显示提示"需要出生地点" |
| 无强相位 | 显示"当前较平稳"空状态，不硬凑解读 |
| 无大型结构 | 不显示空网络，替换为主导相位列表 |
| AI 服务未配置 | AI 入口显示"暂不可用"，不影响其余模块 |
| 服务器返回不完整 | 只解读已返回事实，缺失字段显示降级提示 |

## 7. 每个盘型必须具备的设计规格

每个新盘型开始实现前，至少要写清：

```text
盘型目标：
  用户打开这个盘最想知道什么？

可靠事实：
  服务器能返回哪些事实？哪些不能返回？

右侧模块：
  固定几张卡？每张卡说什么？用什么可视化？

底部解读：
  有哪些 Tab？每个 Tab 用什么阅读结构？

语料：
  哪些来自 Obsidian？哪些已迁移进项目？哪些还缺？

可视化：
  哪些事实用进度条、堆叠条、时间线、标签、卡片、表格？

降级：
  缺出生时间、缺地点、缺相位、无强信号时怎么显示？

禁忌：
  哪些表达不能出现？

验证：
  用哪些样例证明不是只适配当前盘？
```

如果这些没有写清，就不应该直接进入 UI 实现。

## 8. 新盘型设计模板

设计新盘型时，按以下步骤推进：

### 第一步：读材料

```text
1. AGENTS.md
2. docs/agent-handoff.md
3. docs/chart-insight-design-standard.md（本文件）
4. 对应盘型 Obsidian 目录
5. 已有同类盘型实现（优先参考次限盘）
```

### 第二步：列可靠事实

确认服务器能返回什么。凡服务器没返回、也没有可靠算法支持的，不能进入"计算事实"。

### 第三步：设计右侧即时解读

回答"用户一眼看这张盘时，最需要知道什么"。固定模块，每个模块写清 3.2 要求的全部字段。

### 第四步：设计底部展开解读

每个 Tab 写清第 4.2 要求的全部字段。

### 第五步：迁移语料

从 Obsidian 提炼语料，改写为消费者可读文案，写入项目 corpus 文件。

### 第六步：实现分层

```text
后端事实 → builder → corpus → presentation rules → React → CSS
```

### 第七步：验证

- 不是只适配当前盘样例
- 有空状态和降级测试
- 每个图形有真实数据来源和映射说明
- 逐张对照 Obsidian 视觉示意
- 摘要与详情都有已审核语料来源
- iPhone 12 mini 宽度下无不可读重叠
- 架构检查和 lint 通过
- 更新交接文档

后续任何盘型完成后，审核者应检查：

- [ ] 是否读过并遵守 AGENTS.md
- [ ] 是否把 Obsidian 有用内容迁移进项目，而不是运行时依赖
- [ ] 是否明确服务器/客户端/AI 边界
- [ ] 是否有项目内 corpus 和 presentation rules
- [ ] 是否达到次限盘同等颗粒度
- [ ] 是否有固定右侧模块和底部结构
- [ ] 是否有空状态和降级规则
- [ ] 每个可视化是否能追溯到真实计算事实，没有示例分数或假时间线
- [ ] 是否逐张达到 Obsidian 示意的视觉颗粒度，而非通用组件替代
- [ ] 是否先显示消费者结论，专业参数进入展开层
- [ ] 每张卡片是否有一句摘要和约 100 字详情，且来自已审核语料映射
- [ ] 中文界面是否纯中文、英文界面是否纯英文，默认是否为英文
- [ ] 轮盘是否有刻度、宫位、四轴、星体度数/状态，且小屏可读
- [ ] `Aspects` 是否为单盘三角矩阵或比较盘交叉矩阵
- [ ] Today 是否为主线、波形、四领域可视化和信号驱动的接下来节奏，而不是四盘参数页
- [ ] 是否完成 iPhone 12 mini、Dynamic Type 和 VoiceOver 检查
- [ ] 是否避免内部话术进入消费者 UI
- [ ] 是否避免硬编码当前样例
- [ ] 是否更新交接文档
- [ ] 是否通过架构检查和 lint
- [ ] 是否没有误改部署、分支、密钥或无关业务

## 10. Obsidian 文档 Frontmatter 规范

所有 Obsidian 目录下的 `.md` 文件必须包含完整的 YAML frontmatter，用于追踪文档来源和变更责任。

### 10.1 必填字段

| 字段 | 类型 | 说明 | 示例 |
|---|---|---|---|
| `created` | date | 文件首次创建日期（YYYY-MM-DD） | `2026-07-28` |
| `updated` | date | 文件最后修改日期（YYYY-MM-DD） | `2026-07-28` |
| `author` | string | 文件创建者 | `teleagent` |
| `modified_by` | string | 文件最后修改者 | `teleagent` |

### 10.2 修改者取值

| 取值 | 含义 |
|---|---|
| `teleagent` | 星辰超级智能体（TeleAgent） |
| `codefree` | CodeFree |
| `codex` | OpenAI Codex / 同类编码 agent |
| `human` | 人工编辑 |

如果连续多次由同一修改者修改，`modified_by` 只写最近一次的修改者。

### 10.3 规则

1. **新建文件**：必须填写全部四个字段（`created`、`updated`、`author`、`modified_by`）
2. **修改已有文件**：必须更新 `updated` 和 `modified_by`，不得修改 `created` 和 `author`
3. **合并修改**：同一次任务中修改多个文件，`updated` 写同一天日期，`modified_by` 写实际执行者
4. **AIGC 水印**：系统自动注入的 `AIGC` 字段由写入工具管理，不属于本规范范围，无需手动维护

### 10.4 完整示例

```yaml
---
created: 2026-07-28
updated: 2026-07-28
author: teleagent
modified_by: teleagent
---
```

多次修改后：

```yaml
---
created: 2026-07-26
updated: 2026-07-28
author: codefree
modified_by: teleagent
---
```
